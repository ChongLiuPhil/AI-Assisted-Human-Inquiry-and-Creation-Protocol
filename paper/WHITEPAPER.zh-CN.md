# Human–AI Research Collaboration Protocol
## 一种以仓库为中心的持久、可审计、人类治理研究架构

## 摘要

AI 系统如今已经能够参与远超单次问答的研究过程：它们可以检索文献、重构论证、形式化思想、起草章节、修订手稿、维护参考文献，并在较长时期内协助发展书籍或研究计划。然而，大多数人机协作仍然建立在一个脆弱基础上：某一个 AI 系统的对话上下文。重要的人类决定滞留在聊天历史中；AI 生成的重新表述可能逐渐变得与作者自己的承诺难以区分；临时格式默认值可能被误认为稳定偏好；而新的 Agent 往往无法在没有重新读取旧对话的情况下重建项目究竟意味着什么。

**Human–AI Research Collaboration Protocol（HARC）** 提出一种以仓库为中心的替代方案。HARC 不把 GitHub 仅仅当作成品文本的存储位置，而把它视为人机研究关系的持久、受版本控制的状态。它区分人类作者的实质性承诺、呈现意图、AI 维护的论证操作性表示、证据、历史决定与派生手稿。它还引入新的人类反馈路由规则、版本化的人类 framework approval，以及 Framework Approval 与 Final Artifact Approval 的区分。其目标是在跨越上下文窗口与可替换 Agent 的同时，仍然保存人类思想能动性、可追溯性与可纠错性。

HARC 不是一种“AI 应取代作者身份”的理论。它是一套协作协议，目标是把人类意图与 AI 转化之间的边界表达得足够明确，使长期协作即使包含大量 AI 下游工作，仍然可以在人类思想治理之下运行。

## 1. 问题：没有持久思想状态的协作

当代 AI 界面主要围绕“对话”优化。这对于局部任务很有效，但严肃研究项目并不只是连续的 prompt 与 reply。它是一个不断变化的系统，其中包括主张、定义、证据、未决问题、形式选择以及可能持续数月或数年的承诺。

当项目主要存在于聊天历史中时，会出现若干结构性问题。

### 1.1 语义漂移

人类可能先表达一个粗糙但在哲学上重要的命题。AI 随后给出更清楚、更可辩护的表述。这个改写可能有价值，但经过多轮修订后，它可能悄悄被当成人类“一开始本来就是这个意思”。

文本变得更好，而意义层面的作者来源却变得更不清楚。

这并不只是普通版本控制问题。Git 可以说明句子 A 变成了句子 B，但普通文本历史本身不会编码：

- 是人类改变了立场；
- 还是 AI 提出了重新解释；
- 人类是否接受了该提议；
- 修改是否只是文体性的；
- 或某个临时起草选择是否意外变成了权威状态。

因此，HARC 把语义状态本身视为必须显式表示的对象。

### 1.2 上下文窗口依赖

长项目可以超过任何单一 AI 对话的容量。即使某个平台提供记忆功能，这种记忆也可能不完整、不透明、依赖特定账号、无法迁移到另一个模型，或者不适合作为正式学术审计轨迹。

结果会形成一个悖论：AI 让大型项目更容易被生成，却可能让它们更难保持连贯。

HARC 的回答是把持久状态外部化到仓库中。

### 1.3 结构不透明

长篇手稿并不是每一次思想决定的理想操作界面。如果一本书有 15 万字，人类不应为了判断“第六章现在是否仍然支持中心命题”而每次重新阅读全部 15 万字。

人类需要一个压缩后的思想架构表示：作品主张什么、各部分为什么彼此连接、每一章贡献什么、哪些反对意见尚未解决、哪些主张仍是 provisional。

HARC 把这称为 **Operational Argument Representation（操作性论证表示）**。

### 1.4 呈现漂移

AI Agent 还会做大量细小的呈现选择：标题层级、页边距、引用样式、字体、语气、脚注约定、视觉密度以及文档结构。

其中有些只是临时实现默认值，有些是发布渠道要求，有些才是真正的作者偏好。如果这些类别不被区分，偶然默认值就可能被误记为作者意图。

因此，HARC 明确把实质内容与形式/呈现分离。

### 1.5 Agent 交接失败

一个持久研究系统不应要求永远使用同一个 AI Agent。模型会变化，平台会变化，工具会变化；项目也可能让不同 Agent 分别负责研究、统计、编辑或排版。

如果项目意义只存在于某一个 Agent 的对话历史，那么这个 Agent 实际上已经成为存储层的一部分。

HARC 追求一个更强的不变量：

> **AI Agent 可以被替换，但研究状态不能被替换掉。**

## 2. 以仓库为中心的研究记忆

HARC 把仓库视为一种**外显化的认识记忆（externalized epistemic memory）**：它持久表示项目当前意味着什么、如何走到当前状态、哪些问题仍未解决，以及成果应怎样被表达。

这并不意味着每一条聊天消息都应该进入 GitHub。如果仓库只是堆满原始聊天 transcript，那么我们只是把上下文问题从一个位置搬到了另一个位置。

因此，协议使用一个**状态提升规则（promotion rule）**：

> 如果丢失某条人类指令会改变一个新的、能力合格的 Agent 应如何继续项目，那么这条指令就应被提升为持久仓库状态。

这样，临时对话被转化为结构化项目记忆。

因此，仓库不只是档案库，也是人类与 AI 参与者之间当前的协调媒介。

## 3. 规范性层级

HARC 把普通 AI 辅助写作中经常混在一起的功能拆分开。

### 3.1 Content Core：人类究竟是什么意思

**Content Core** 记录人类作者当前有效的实质性承诺。

它回答诸如：

- 项目试图建立什么？
- 哪些区分重要？
- 哪些命题当前有效？
- 哪些立场只是暂定？
- 哪些问题被有意保持开放？

只有人类原创承诺，或者已经被人类明确接受或修改的 AI 提议，才能进入这里。

Content Core 不应膨胀成完整手稿。它的价值来自压缩与权威性。

### 3.2 Form Core：人类希望作品怎样表达

**Form Core** 独立于研究内容，记录呈现意图。

项目因此可以区分：

- AI 临时选择的字体；
- 期刊要求的引用样式；
- 某一本书特有的版式；
- 真正跨项目稳定的作者偏好。

这样可以防止技术默认值变成虚假的作者审美记忆。

### 3.3 Decision Log：当前状态如何形成

当前状态文件应保持简洁，但简洁也带来风险：重写当前状态可能删除“决定是怎样形成的”。

**Decision Log** 通过保存时间顺序审计轨迹解决这个问题。

当前命题可以改变；旧命题可以从 active Content Core 中消失，但仍然保留在历史决定记录中。

因此形成两类记忆：

- **active memory** — 当前治理工作的状态；
- **historical memory** — 项目如何走到这里。

### 3.4 Operational Argument Representation：项目在结构上究竟说什么

**Working Argument Map** 是 AI 维护的当前作品结构模型。

它不只是目录，而应显式暴露推论结构，例如：

- 命题 A 依赖前提 B 与 C；
- 第三章建立 B；
- 第四章处理反对意见 D；
- 第六节限制 A 的适用范围；
- 主张 E 仍然只是 AI 提议，尚未经人类批准。

这应成为结构性人机讨论的主要界面。

人类不必检查每一段扩写文字，才能对作品架构进行推理。

### 3.5 Evidence Layer：什么约束负责任的主张

人类作者权威涉及“作者打算表达什么”，并不意味着证据可以被省略。

文献、数据、形式推导、计算与来源核验属于 **Evidence Layer（证据层）**。

当证据与 Content Core 冲突时，正确做法既不是：

- 静默改写人类立场；

也不是：

- 为了保持一致而隐藏反面证据。

冲突应成为显式项目状态，并返回人类进行决定。

### 3.6 Derived Artifact：被扩写的成果

论文、书籍、报告或文章属于 **Derived Artifact（派生成果）**。

它可以远比上游状态庞大。AI 可以协助产生解释、例子、文献讨论、过渡、表格与文体扩展。

但派生成果并不会因此反过来对治理它的人类上游状态取得独立权威。

## 4. 三类人类反馈

HARC 的一个核心操作规则是：人类指令应在持久化之前先被分类。

### CONTENT

改变作品意味着什么、论证什么、假设什么、区分什么或得出什么结论。

### FORM

改变成果怎样表达：字体、版式、体裁、引用、视觉与呈现约定。

### PROTOCOL

改变协作怎样进行：持久化、批准门、交接、版本、Agent 责任。

一条指令可以同时拥有多个标签。

这种区分之所以重要，是因为每一类变化的传播路径不同。一个哲学命题变化不能只在第八章做局部修改；字号变化不应被写成思想承诺；批准流程变化也不应改写研究论证。

这就是协议的**上游优先原则（upstream-first principle）**：先更新权威状态，再把变化传播到派生成果。

---

## 5. 从 AI 维护的结构到人类批准的 Framework

操作性论证图之所以有价值，正是因为它可以灵活变化。但灵活性也带来作者性问题：AI 可以在人类从未看到的情况下重新组织论文。

因此，HARC 区分 **Working Framework** 与 **Approved Framework Snapshot**。

### 5.1 Working Framework

可修改、由 AI 维护、允许实验。

它可以包含拟议重构、尚未解决的张力与 AI 生成建议。

### 5.2 Approved Framework Snapshot

一个由人类明确审阅并确认的紧凑思想架构版本。

一旦批准，它会被冻结为类似：

`FW-001`

这样的标识。

实质性变化会产生新版本，而不是静默重写旧版本。

这形成了普通手稿版本控制无法单独提供的**语义审计轨迹**。

未来仓库审阅者可以问：

- 人类实际批准了哪个 framework？
- 何时批准？
- 之后发生了什么变化？
- 当前手稿是否仍然实现该 framework？

## 6. 一种不同的人类注意力分配方式

HARC 的一个实际动机是：AI 产生长文本的速度远快于人类逐行检查文本的速度。

如果唯一可接受的协作模式要求人类在每一次 AI 修订后手工重读每一句 provisional 文本，那么人类会成为吞吐瓶颈，AI 的许多潜在收益会消失。

HARC 提议把人类注意力集中在更高价值的层次：**思想架构（intellectual architecture）**。

对于长篇成果，人类应能够审阅一个压缩表示，其中包含：

- 主要命题；
- 论证依赖关系；
- 关键区分；
- 章节/小节功能；
- 限制条件；
- 未决问题。

在人类批准该 framework 后，AI 可以在 framework fidelity 约束下进行大量下游展开。

这并不意味着最终发表责任消失，而是区分两个检查点。

### Gate A：Framework Approval

确认思想架构。

### Gate B：Final Artifact Approval

按照相关外部标准要求的程度，确认实际准备投稿、出版或公开发布的具体版本。

因此可以说：

> **Framework Approval 界定实质性思想作者责任的中心；Final Artifact Approval 界定公开学术问责的门槛。**

## 7. Framework 向最终作品的投影

如果 framework 只存在于仓库 metadata 中，它对于协作有用，但对读者不可见。

因此，HARC 要求在 Approved Framework 与最终成果的读者总览之间建立一种**投影关系（projection relation）**。

对于学术论文，摘要和引言应忠实表达主要问题、命题、论证动作、贡献与路线图。

对于书籍，导论或总览章节应说明治理性 framework，以及主要章节各自承担什么角色。

总览不需要逐字复制仓库语言，但必须保持结构忠实。

这提供了一个很有用的验证测试：

- 如果 overview 无法准确表示 Approved Framework，那么 overview 或手稿已经不同步；
- 如果手稿出现 Approved Framework 中没有的重大结论，那么手稿可能已经漂移出人类批准范围。

## 8. 语义版本控制

Git 提供文本版本控制。HARC 在此之上增加一层**语义版本控制（semantic version control）**。

一次 commit 可以告诉我们哪些字符发生变化。HARC 状态试图进一步告诉我们这是什么类型的变化：

- 人类修改了命题；
- 人类接受了 AI 提议；
- AI 提出了结构，但人类尚未接受；
- FORM 改变而 CONTENT 没变；
- 证据产生了冲突；
- Approved Framework 已经过时。

这种区分之所以关键，是因为研究项目并不只是一个文本文件，而是一个不断变化的承诺网络。

---

## 9. 超越上下文窗口的扩展

HARC 并没有消除上下文窗口限制，而是把长期记忆移到模型之外。

仓库在普通存储意义上可以持续增长，而每一个 Agent 只读取当前工作需要的部分。

因此，协议区分：

### 紧凑活动状态

- Content Core；
- Form Core；
- 最新 framework；
- 当前 Argument Map；
- 最近决定。

### 扩展历史状态

- 完整 Decision Log；
- Evidence archives；
- 旧 Framework；
- 历史草稿；
- 研究笔记。

历史状态变大后，系统应增加索引、摘要与按日期归档，而不是让 active cores 无限膨胀。

设计目标不是 infinite context，而是**持久、可选择检索的状态**。

## 10. Agent 可替换性与平台独立性

HARC 初始采用 GitHub，因为 GitHub 提供版本历史、分支、审阅、结构化文件和广泛工具支持。

但概念架构并不依赖某一个具体模型。

一个遵循 HARC 的项目应能在下列变化中保持可理解：

- 从一个 AI 模型换到另一个模型；
- 从一个专门 Agent 换到另一个；
- 从一个厂商换到另一个；
- 从一个对话换到另一个。

这把人机关系从：

`Human <-> One Persistent Assistant`

转变为：

`Human <-> Persistent Research State <-> Interchangeable Agents`

连续性属于研究状态，而不是 AI 身份。

---

## 11. 自举与协议演化

HARC 本身也应当按照 HARC 原则发展。

因此，本仓库包含 Protocol Core 与 Decision Log，用来区分：

- 人类原创设计承诺；
- AI 扩展；
- 后续社区提议；
- 已接受的协议变化。

这种 self-hosting（自举）特性本身提供一个实践测试：如果协议不能透明地治理自己的演化，就很难相信它能够治理更复杂的研究项目。

---

## 12. 局限与开放问题

HARC v0.1 有意保持克制。

### 12.1 它不能保证真理

显式 provenance 不会让论证自动变真。证据审查、专业知识与批判性推理仍然不可缺少。

### 12.2 它不能解决所有 authorship 问题

不同学科、机构和出版商可能对披露、最终批准与可接受 AI 使用提出不同规则。HARC 提供内部 provenance 与责任检查点，但不能取代外部政策。

### 12.3 它会增加维护成本

规范状态必须持续更新。如果 Agent 没有把重要决定提升到上游状态，仓库就会变得过时。

因此，未来版本需要轻量自动化与验证工具。

### 12.4 Framework 压缩可能遗漏 nuance

紧凑 framework 有用，正是因为它进行压缩。但过度压缩可能隐藏重要限定条件。

因此，framework 设计本身成为一种思想技能，而不仅是文书工作。

### 12.5 人类确认可能变成仪式性动作

Approval Gate 只有在人类真正理解所批准内容时才有意义。未来应研究如何让 Framework Review 足够高效，同时又不退化成 checkbox。

---

## 13. 未来发展

潜在扩展包括：

- 自动仓库初始化；
- 规范文件的 schema validation；
- Approved Framework 与 manuscript 的同步检查；
- 可视化 argument graph；
- claim/section-level provenance annotation；
- 与 citation manager 和 research database 集成；
- 用 Pull Request workflow 支持 Framework Approval；
- 可复用作者 Form Profile；
- local-first 与非 GitHub backend；
- multi-human / multi-agent governance；
- 对 HARC 是否降低 semantic drift 与 onboarding cost 进行经验评估。

---

## 14. 结论

AI 辅助研究需要的不只是更好的生成能力，还需要持久协作架构。

HARC 的中心提议是：人类意图、AI 表示、证据、呈现意图、历史决定与最终表达，不应被压缩进一个不断变化的手稿或一段会消失的聊天历史。

通过把这些功能外部化为显式仓库状态，HARC 试图让长期人机研究变得：

- 持久；
- 可审计；
- 可跨 Agent 迁移；
- 结构可检查；
- 可以被证据纠正；
- 并在人类最重要的批准层——作品的思想架构——保持治理。

协议可以用一句话概括：

> **把研究状态外部化，把不同权威层分开，批准核心 Framework，并让 AI 扩写始终可追溯到人类实际意图。**
