# Human–AI Research Collaboration Protocol
## 一种以 GitHub 为持久研究状态的人机协作架构

**工作白皮书 v0.1（中文版）**

## 摘要

当 AI 开始参与长期研究、论文写作、书籍开发和持续思想探索时，真正困难的问题已经不只是“如何生成更好的文字”，而是：**如何让一个长期项目在跨越大量对话、多个模型、多个 Agent 和漫长时间之后，仍然保持人类作者的思想连续性、责任边界和可追溯性。**

Human–AI Research Collaboration Protocol（HARC）提出一种以 GitHub 为核心的解决方案。它不把 AI 对话框视为项目的长期记忆，而把版本化的仓库文本视为持久、显性、可审计的共同研究状态。协议明确区分：人类作者的研究内容意图、人类作者的形式表达意图、AI 对论证结构的操作性表示、证据层、历史决策以及最终扩写成果。

HARC 进一步引入三个关键机制：第一，所有重要的人类反馈在进入最终文本之前，都先按照 `CONTENT / FORM / PROTOCOL` 分类并写入相应基础文档；第二，AI 所维护的论证框架只有经过人类明确阅读和确认后，才成为版本化的 Approved Framework；第三，框架确认与最终作品确认相互区分，使人类可以把主要注意力集中在思想和论证结构上，同时保留正式发表前的最终责任节点。

HARC 的目标不是让 AI 成为隐藏作者，而是建立一种可持续的人机研究基础设施，使 AI 可以被替换，而研究状态不随某个 Agent 或某个聊天窗口一起消失。

---

## 一、为什么普通 AI 对话不适合作为长期研究基础设施

一个短问题可以通过一次对话解决，但一篇论文、一本书或一个持续数年的研究计划不是一串彼此独立的问题。它包含不断变化的命题、定义、结构、证据、反对意见、形式偏好和决策历史。

如果这些内容主要存在于 AI 平台的聊天上下文中，会出现几个结构性问题。

### 1. 语义漂移

人类作者最初提出一个较粗糙但重要的观点。AI 为了让论证更清晰、更可辩护，对它进行改写。改写可能是好的，但在多轮协作之后，AI 的版本可能逐渐被当作“作者原本就是这个意思”。

于是，文本越来越成熟，而“谁真正决定了核心含义”越来越不清楚。

传统 Git 可以记录哪一段文字发生变化，却不能自动告诉我们：这是人类改变立场，还是 AI 做了一个尚未被确认的解释。

因此，长期人机研究需要的不只是 textual version control（文本版本控制），还需要一种 **semantic version control（语义版本控制）**。

### 2. 上下文窗口依赖

无论上下文窗口多大，一个持续发展的研究项目最终都可能超过单次对话能够承载的规模。

即使某个平台有账号记忆，它也可能不透明、不完整、无法迁移到其他模型或其他供应商，也不适合作为正式的研究审计记录。

所以长期研究不应把某个 AI 平台本身当作唯一记忆层。

### 3. 长篇成果的结构不可见

如果一本书有十几万字，人类作者不应该每次讨论结构时都必须重新阅读全部正文。

更合理的方式是维护一个比正文短得多、但能够显示全文核心结构的操作性文本：

- 全书究竟要证明什么；
- 哪个章节负责哪个论证步骤；
- 哪些命题互相依赖；
- 哪些问题仍未解决；
- 哪些内容只是 AI 建议。

这就是 HARC 的 Operational Argument Representation。

## 二、GitHub 不只是存稿，而是“外显化研究记忆”

HARC 把 GitHub 看作一种 externalized research memory（外显化研究记忆）。

核心原则是：

> **聊天是临时交互界面，仓库才是持久共同研究状态。**

这并不意味着每一句聊天都应该保存。

协议采用一个简单的“晋升规则”：

> 如果明天换成一个完全新的 AI Agent，而丢失当前对话中的某条人类指令会改变它应该如何继续项目，那么这条指令就应该被晋升为 GitHub 中的持久状态。

因此，仓库不是聊天记录仓库，而是对重要状态进行结构化保存的地方。

## 三、HARC 的基础文件层级

### 1. Content Core：人类到底想主张什么

`CONTENT_CORE.md` 只保存当前有效的人类研究内容意图。

它回答：

- 中心问题是什么；
- 人类作者当前真正主张什么；
- 哪些命题只是暂定；
- 哪些区分必须保留；
- 哪些问题仍然开放。

AI 可以提出新论点，但在得到人类接受以前，不能把这些论点直接写成作者主张。

### 2. Form Core：人类希望作品怎样呈现

`FORM_CORE.md` 与研究内容独立。

它保存：

- 作品类型；
- 语言与文体；
- 字体字号；
- 页面与段落系统；
- 标题结构；
- 引用与参考文献呈现；
- 图表风格；
- 可跨项目复用的作者形式偏好。

这可以避免一个常见问题：AI 为了临时生成文档选择了某种字号或格式，后来新的 Agent 却误认为“这是作者一直以来的个人偏好”。

### 3. Decision Log：保存思想和规范的发展历史

当前状态需要保持简洁，但研究历史又不能消失。

因此 `DECISION_LOG.md` 保存重要的人类决策：何时增加了一个主张、何时否定了某种解释、何时接受了 AI 的建议、何时修改了形式要求。

Content Core 表示“现在以什么为准”，Decision Log 表示“我们如何走到这里”。

### 4. Working Argument Map：人机真正讨论结构的主要界面

`argument-map.md` 是由 AI 主要维护的操作性论证表示。

它不是简单目录，而是应当显示：

- 中心命题；
- 主要前提；
- 命题之间的支持和限制关系；
- 各章节承担什么论证功能；
- 最强反对意见；
- 证据依赖；
- 等待人类决定的问题；
- 尚未被人类接受的 AI 提案。

对于大型项目，人类与 AI 的主要思想讨论应尽可能发生在这个层面，而不是每次都直接对几十万字正文进行整体操作。

## 四、CONTENT、FORM、PROTOCOL 三类反馈路由

HARC 要求 AI 在保存重要人类反馈以前先判断它属于什么性质。

### CONTENT

改变作品“说什么”。

例如：修改一个命题、增加一个区分、否定一种解释、改变论证范围。

典型传播路径：

`人类决定 -> Decision Log -> Content Core -> Argument Map -> 最终文本`

### FORM

改变作品“怎么呈现”。

例如：字体、排版、章节风格、引文形式、书籍还是论文、视觉效果。

典型传播路径：

`人类决定 -> Decision Log -> Form Core -> 排版/渲染实现 -> 最终作品`

### PROTOCOL

改变“人类和 AI 怎么合作”。

例如：是否必须先更新 GitHub、如何确认框架、如何换 Agent、如何进行版本审批。

典型传播路径：

`人类决定 -> Decision Log -> Protocol 文档 -> Agent 行为`

一条反馈可以同时拥有多个标签。

## 五、为什么要有人类确认的 Framework Snapshot

AI 维护的 Working Argument Map 必须能够灵活变化，但它不能自动代表人类作者。

因此 HARC 区分：

- **Working Framework**：AI 维护、随时可改、用于讨论；
- **Approved Framework Snapshot**：人类明确阅读并确认过的版本。

一旦确认，就冻结为：

`FW-001`

以后如果核心论证结构发生实质变化，必须产生：

`FW-002`

而不是偷偷覆盖旧版本。

这样，一个新的 Agent 或未来的研究者可以明确知道：

- 人类作者究竟确认过什么；
- 什么时候确认；
- 后续又发生了什么变化；
- 当前正文是否仍然忠实于该框架。

这就是 HARC 所谓的 semantic audit trail（语义审计轨迹）。

---

## 六、把人类注意力集中在真正重要的层面

AI 的一个重要特征是可以非常快速地生成大量展开文本，而人类阅读速度并没有同比提高。

如果协作模式要求人类在每一次 AI 修改后重新逐字审查几十万字，那么 AI 并没有真正解决长期研究的结构性问题。

HARC 因而提出：人类最重要的高强度审查应集中在 intellectual architecture（思想/论证架构）上。

人类需要清楚知道并确认：

- 核心命题；
- 论证链；
- 主要区分；
- 章节之间的逻辑关系；
- 范围限制；
- 有意保留的问题。

确认之后，AI 可以在这个框架下进行大量扩写。

因此 HARC 区分两个 Gate：

### Gate A：Framework Approval

确认作品的核心思想和论证架构。

### Gate B：Final Artifact Approval

在正式投稿、出版或公开发布前，对具体发布版本进行最终确认，其程度服从相关学科、期刊、出版社或机构要求。

简要来说：

> **框架确认界定实质性思想作者身份的中心；最终作品确认界定公开学术问责的门槛。**

---

## 七、确认过的框架必须投影到作品导论或摘要

如果 GitHub 中的人类确认框架与最终读者看到的作品完全脱节，那么框架只是一种内部管理工具。

HARC 更进一步要求：人类确认的核心结构应在读者可以看到的 overview 中被忠实表达。

例如：

- 学术论文：摘要 + 引言；
- 普通文章：开头的论题和论证路线；
- 书籍：导论/总论 + 章节路线图；
- 报告：执行摘要 + 结构说明。

这形成一个非常重要的检查机制：如果导论已经无法准确表达 FW-001，那么要么导论错了，要么正文已经漂移，要么框架需要更新。

---

## 八、不是无限上下文，而是可无限增长的外部状态

HARC 并不是说 AI 获得了无限上下文。

更准确地说，它让项目不再被绑定在某一个对话窗口上。

项目可以拥有不断增长的历史状态，但新的 Agent 不需要一次性读取所有内容。

HARC 将信息分为：

### 当前活动状态

- Content Core；
- Form Core；
- 最新 Framework；
- Argument Map；
- 最近决策。

### 可增长历史状态

- 完整决策历史；
- 证据档案；
- 旧 Framework；
- 旧稿；
- 研究笔记。

随着历史变长，可以增加索引、摘要和归档，只在需要时进行选择性检索。

因此目标不是 infinite context，而是 persistent and recoverable state（持久且可恢复的状态）。

---

## 九、AI Agent 应该可以替换

HARC 希望把长期连续性从 AI 身份转移到研究状态本身。

传统想象是：

`Human <-> one persistent AI assistant`

HARC 更接近：

`Human <-> persistent research repository <-> interchangeable AI agents`

新的模型、新的供应商、新的专业 Agent 都可以接手，只要它们能够读取 GitHub 中的显性状态并遵守协议。

可以把这一点概括为：

> **AI Agent 可以替换，研究状态不能随 Agent 一起丢失。**

---

## 十、局限与后续工作

HARC v0.1 仍有明显限制。

第一，它不能保证研究内容是真的。协议只能提高结构透明度，不能替代证据、专业知识和批判性判断。

第二，Framework 的压缩本身可能丢失细节，因此“如何做高质量的论证结构压缩”是一个重要研究问题。

第三，人类确认可能变成形式化点击。如果作者并未真正理解 Framework，Approval Gate 就失去意义。

第四，维护这些文件会产生额外成本，因此未来应开发自动化工具来降低同步成本。

后续可以发展：

- 自动初始化仓库；
- 机器可读 schema；
- Framework 与正文的一致性检查；
- 可视化 argument graph；
- claim-level provenance；
- 多人类、多 Agent 协作治理；
- GitHub 以外的平台实现；
- 对 semantic drift 是否真正降低进行实验评估。

---

## 结论

AI 辅助研究未来真正需要的，不只是生成能力，而是一套持久的协作架构。

HARC 的核心不是要求 AI 少做工作，而是要求 AI 的工作始终能够被追溯到明确的人类意图、明确的结构确认、明确的证据约束和明确的发布责任。

它把长期研究从“一个越来越长的聊天记录”转变成“一个可以被不同 Agent 读取、检查、继续和纠正的显性研究状态”。

可以用一句话概括：

> **把研究状态外显化，把不同权威层分开，让人类确认核心框架，并让 AI 的扩写始终可以追溯到人类真正确认过的内容。**
